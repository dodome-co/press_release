# 計画書：AI による要旨の文書案（チャット・音声入力）

仕様書（[仕様書.md](仕様書.md)）の F24「AI による要旨の文書案作成」を、発表の前に作るための計画。仕様書に反映する前の、たたき台。決めたことは8章、日程は10章。

## 1. 全体の流れ

```
① クライアントが、サービスの内容と、要旨の元になる情報を、チャットか音声で入力する
② 情報が足りない点を、AI が質問する。クライアントが答える（そろうまで、くり返す）
③ 情報がそろったら、AI が、タイトル・サービスや商品の特徴（最大3つ）・要旨をまとめる
④ AI が、プレスリリース全体を A4 1枚にまとめる（情報に優先順位をつけ、優先順位の低い情報は削る）
⑤ 管理者が確認して、直して、承認する
```

- 最後に確かめて承認するのは、これまでどおり管理者。AI がまとめた内容を、そのまま承認することはしない。
- 日時・場所・当日のスケジュール・取材の申込方法と締切・写真は、これまでどおり、入力画面で入力する。チャットと音声で聞くのは、「サービスの内容」と「要旨の元になる情報」の2つ。

## 2. チャットで入力する場合

- チャットで扱うのは、次の2つ。
  1. サービスや商品の内容
  2. 要旨に関する質問（取材してほしい内容／なぜ今これを行うのか／伝えたいこと）
- クライアントが、チャットで答えを入力する。情報が足りない点があれば、AI がチャットで質問する。
- 情報が十分にそろったら、AI が、次をまとめる。
  - サービスや商品の特徴（最大3つ。箇条書き）
  - 要旨（前文）
  - タイトルの候補（AI が2〜3個出す）
- **サービスの概要は書かない。** 特徴だけを、箇条書きで出す。

## 3. 音声で入力する場合

- チャットの代わりに、音声を使う。扱う内容は、チャットと同じ2つ（サービスの内容、要旨に関する質問）。
- クライアントが、話して答える。情報が足りない点があれば、AI が、**音声と文字の両方で**質問する。クライアントは、さらに話して答える。
- 情報が十分にそろったら、AI が、次をまとめる。
  - サービスや商品の特徴（最大3つ。箇条書き）
  - 要旨（前文）
  - タイトルの候補（AI が2〜3個出す）
- **サービスの概要は書かない。** 特徴だけを、箇条書きで出す。

**タイトル**：チャットでも音声でも、AI が候補を2〜3個出し、クライアントが選ぶ。選んだあと、管理者が直せる。

## 4. A4 1枚にまとめる

- AI が、プレスリリース全体（タイトル、要旨、取材のご案内、特徴、会社概要、お問い合わせ先、写真）が A4 1枚に収まるように、文章の長さを調える。
- 収まらないときは、情報に優先順位をつけて、優先順位の低いものから削る。
- 管理者の画面には、AI が削った情報も表示する（必要なら、管理者が戻せるように）。

優先順位（決定）：

| 優先 | 情報 | 理由 |
| --- | --- | --- |
| 高（削らない） | タイトル、日時・場所、取材の申込方法と締切、お問い合わせ先 | 記者が取材に来るために、必ず要る |
| 中 | 要旨、特徴 | 短くするが、なくさない |
| 低 | 当日のスケジュールの細かい行、会社概要の一部の行（資本金・従業員数など）、写真の2枚目 | 取材の判断への影響が小さい |

- 「A4 1枚に収まったか」は、文字数の目安で判断する（実際の Word の見た目は、承認のときに管理者が仮の Word で確かめる）。

## 5. 管理者がすること

- 書類の確認画面で、AI がまとめたタイトル・特徴・要旨と、クライアントとのやりとり、AI が削った情報を見る。
- 直して、承認する（差し戻しも、これまでどおりできる）。
- 承認の前に、仮の Word で、A4 1枚に収まっているか確かめる（今もある機能）。

## 6. 今の作りから変えること

### 6-1. 画面

| 画面 | URL | 変えること |
| --- | --- | --- |
| 書類の入力・編集（クライアント） | `/releases/<id>/edit` | チャットの欄（または音声のボタン）を足す。「サービスや商品の概要」「特徴」「要旨の元になる3つの質問」の入力欄をなくし、AI がまとめた結果を表示する。日時・場所などの入力欄は残す |
| 書類の確認（クライアント） | `/releases/<id>` | AI がまとめた内容を確かめてから、提出する |
| 書類の確認・編集（管理者） | `/admin/releases/<id>` | クライアントと AI のやりとり、AI が削った情報を表示する |

**今の入力欄は残さない**（決定）。サービスの内容と要旨の元になる情報は、チャットか音声だけで入力する。そのため、AI が使えないときは、クライアントは、その部分を進められない（7-2 の「AI が使えないとき」）。

### 6-2. Word とデータ

| 変更 | 内容 |
| --- | --- |
| サービスの概要 | 提出に必須でなくする。Word では、空なら出さない（「◆ サービスの内容」の下は、特徴の箇条書きだけにする） |
| 要旨 | AI がまとめた要旨を入れる。`releases.summary_source` を `ai_assisted` にする（列は用意済み） |
| 新しいテーブル：AI とのやりとり | 書類ごとの、クライアントと AI のやりとり（誰が、いつ、何を言い、AI が何を返したか）。入力した方法（チャット・音声）も残す。退会のときは、書類と一緒に消す |
| AI が削った情報 | 書類ごとに残し、管理者の画面に出す |

- データベースの変更は、マイグレーションにして、SQLite と MySQL の両方で確かめる（CLAUDE.md の決まり）。

## 7. 使う技術と注意

### 7-1. 技術（案）

| 分類 | 案 |
| --- | --- |
| AI | Claude API（Anthropic）。Python の公式ライブラリで呼ぶ。足りない情報の質問、特徴・要旨・タイトルのまとめ、A4 1枚への調整に使う。使うモデルは、作るときに、費用と速さで決める |
| 音声を文字にする | ブラウザの音声認識（Web Speech API。Chrome・Edge）。サーバーには、文字になった結果だけが届く |
| AI の質問を読み上げる | ブラウザの読み上げ機能（Web Speech API の音声合成）。費用はかからない |
| 設定 | API キーは、環境変数（開発は `.env`、VM は `/etc/press-release.env`）。コードと Git には入れない |

### 7-2. 注意

- **費用**：Claude API は、使った分だけ料金がかかる。Anthropic のアカウントと、支払いの登録が必要。1つの書類で AI を呼べる回数に、上限を設ける。
- **個人情報**：クライアントの入力を、外部のサービス（Anthropic）に送る。デモではサンプルのデータだけを使う。公開する前に、プライバシーポリシーに書く。ブラウザの音声認識は、ブラウザによっては、音声をブラウザの会社のサーバーに送る。
- **HTTPS**：ブラウザは、多くの場合、HTTPS のページでしかマイクを使わせない。今の VM は HTTP なので、音声入力を見せるには、VM を HTTPS にする作業が要る見込み。作り始める前に、実際に確かめる。
- **AI が使えないとき**（キーがない、通信の失敗、上限を超えた）：分かりやすいエラーを出し、もう一度試せるようにする。それまでのやりとりは消さない。管理者は、これまでどおり、管理者の画面で手で直せる。
- **安全**：AI を呼べるのは、ログインした本人だけ。回数制限を付ける。AI の答えは、HTML として扱わない（文字として出す）。

| --- | --- |
| タイトル | チャットでも音声でも、AI が候補を2〜3個出し、クライアントが選ぶ |
| A4 1枚の優先順位 | 4章の表のとおり |

| API キー | 運営者が Anthropic のアカウントを作り、支払いも運営者。キーは、開発は `.env`、VM は `/etc/press-release.env` に、運営者が書く（チャットに貼らない） |

## 9. やらないこと

- AI がまとめた内容を、管理者の確認なしに確定すること。
- サービスの概要を、AI に書かせること（特徴の箇条書きだけにする）。
- 音声のファイルを、サーバーに保存すること。
- 日時・場所・申込方法・締切・写真を、チャットや音声で聞くこと（入力画面で入力する）。
