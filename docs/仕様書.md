# プレスリリースサポートアプリ 仕様書（たたき台 v0.4）

元資料：仕様書の元となる文書.md を整理・補強したもの。`【要確認】` は未決事項（9章に一覧）。

## 1. 概要

クライアント（企業）が日時・場所・写真などを入力すると、管理者が仕上げたプレスリリース（Word）を受け取れる。さらに有料で、2件目以降のリリース作成、記者発表会の企画・当日の同席、投げ込み交渉代行、記事制作、動画制作を依頼できる Web アプリ。管理者は、作成された書類と依頼内容を確認する。

- 利用者：クライアント（広報担当・中小企業など）、管理者（運営側）
- 技術前提：Python / Flask、決済は Stripe（元資料より）
- **開発環境と本番環境で、一部の部品を切り替える。本番は Google Cloud を使用する。**（忘れないための注意）

| 項目 | 開発環境 | 本番環境 |
| --- | --- | --- |
| 実行基盤 | ローカル（WSL）で `flask run` | Google Cloud の Compute Engine「VM インスタンス」（Linux の仮想マシン。gunicorn と Nginx で Flask を動かす想定） |
| データベース | SQLite（手軽なもの） | Cloud SQL（MySQL） |
| ファイル保存（写真・Word） | ローカルフォルダ | VM のディスク上の専用フォルダ（想定。未確認）。バックアップを取る |
| メール | ログ出力のみ | 【要確認】実際に送信する仕組み（あとで決める） |
| 秘密情報（Stripe キーなど） | `.env` ファイル | VM 上の設定ファイル（読める人を制限し、Git に含めない）。Secret Manager の利用は未確認 |
| Stripe | テストモード | 本番モード |

※ 切り替えは、コード内に書き込まず、環境変数（設定）で行う。

※ 開発の SQLite と本番の MySQL は細かい動きが違うことがある。本番に近い状態で確認するため、公開前に MySQL で動作確認する（または開発も MySQL にそろえる）。

### 書類作成の流れ

| 段階 | 流れ |
| --- | --- |
| **API 導入前**（最初のリリース） | ① クライアントが入力 → ② 日時・場所などの単純項目は、フォーマット（テンプレート）に自動で入る → ③ **要旨（前文）は管理者が書く**。書類を確認・修正する → ④ 承認すると Word で出力される |
| **API 導入後**（第2弾） | ① クライアントが入力 → ② API（AI）が要旨（前文）の**文書案**を作る → ③ 管理者が書類を確認・修正する（案を直す） → ④ 承認すると Word で出力される |

- 要旨（前文）は、どちらの段階でも最後は管理者が確認して仕上げる。違いは、最初から書くか、AI の案を直すか。
- 要旨（前文）とは、「取材してほしい内容」と「社会的意義」を含めた、リリースの冒頭の文章のこと。
- Word は、承認の時点で出力する（提出時には作らない）。

## 2. 目的・背景

- プレスリリースの作り方・配り方（投げ込み）が分からない企業を支援する。
- 書類作成は無料（1件まで）で提供し、有料の周辺サービスで収益を得る。
- 想定する主な顧客：中小企業・個人事業主（広報担当がいない、または少ない）。プレスリリースの作り方・配り方が分からない企業。

| F5 | 書類作成 | 入力内容を HTML 画面でプレビュー確認し、「承認待ち」として提出する。提出後は、承認までの目安（2営業日以内）を表示する（Word 自体はブラウザで表示できないため）。日時・場所などの単純項目は、テンプレートの決まった位置に自動で入る。要旨（前文）は管理者が作成するため、提出時点では空欄。**Word は提出時には作らない** | クライアント | ◎ |

| F5c | 編集 | 管理者が、承認前（承認待ち）の書類について、**要旨（前文）を作成・修正**する（要旨が空のままでは承認できない）。あわせて、その他の項目（タイトル、日時、場所、スケジュール、サービスや商品の概要、特徴、写真、申込方法、締切）も編集できる。編集履歴（誰が・いつ・どの項目を・変更前→変更後）を残す。要旨以外の項目を変更した場合は、承認時のメールとマイページで変更点を知らせる | 管理者 | ◎ |
| F26 | Word 出力 | 運営者が Word で作った雛形（.docx、1種類のみ）に、内容を差し込んで出力する。構成は「Word 雛形の構成」（9章の決定済み）のとおり。空の項目（スケジュール、写真、特徴、会社概要の各行、携帯電話番号など）は、見出しや行ごと表示しない。雛形はプロジェクト内の templates フォルダに置き、Git で管理する | システム | ◎ |

## 8. 非機能要件

- **セキュリティ**
  - パスワードはハッシュ化して保存する。CSRF 対策を入れる。
  - 他人の書類・注文は参照不可（所有者チェック）。
  - アップロードは MIME・拡張子・サイズに加え、画像として開けるか検証する。保存名はランダム化する。
  - 管理者はコマンドでのみ作成する。
  - Stripe の秘密鍵・Webhook シークレットは環境変数で管理し、Git に含めない（`.env` は `.gitignore`）。Webhook は署名検証する。
- **決済**：支払い確定は Webhook のみ。同じイベントを2回受けても二重処理しない（冪等性）。支払いは申込み時の前払い。返金は管理者の操作で Stripe の返金機能を使い、返金額の合計が支払額を超えないようにする。
- **書類の形式**：Word（.docx）。python-docx などで生成し、日本語フォントを指定する。単純項目はテンプレートに差し込み、要旨（前文）は管理者が作成する。AI（API）による要旨の文書案作成は第2弾。承認時に Word を出力する。
- **本番の運用（VM）**：HTTPS で公開する。VM を再起動してもアプリが自動で起動する。OS・パッケージを定期的に更新する。ファイアウォールで必要なポートだけを開ける。写真・Word とデータベースのバックアップを定期的に取る（VM のサーバー管理は運営側の責任）。
- **環境**：Python 3.x、Flask。開発環境と本番環境（Google Cloud）で一部の部品を切り替える（3章の表を参照）。設定は環境変数で切り替える。
- **個人情報**：電話番号・郵便番号・住所を扱うため、プライバシーポリシーと利用規約のページが必要。
- **設定値**：コードに書き込まず、設定で変更できるようにする。対象：無料の書類の上限（1件）、下書きの上限（3件）、タイトルの長さ（全角22文字）、写真の縦横比（1.2以上）、入力欄の文字数（500文字）、承認の目安（2営業日）、画像の大きさの上限（約1,600万画素）、返金の割合、お支払い前の注文の数の上限（5件）。
- **テスト**：認証・アクセス制御・アップロード検証・Webhook を優先して自動テスト化する。

## 11. あとでやること

仕様としては決まっているが、開発の順番の都合で後回しにしているもの。9章の「未決事項」（決めること）とは別に、「作ること・直すこと」を置く。

### About Us のようなページ（会社案内）
- 運営者の紹介ページ（About Us）を作る。内容を表示するだけの静的なページで、データベースや決済には関係しない。後から追加しても、ほかの機能に影響しない。
- 決めること：
  - ログインしていなくても見られるようにするか（会社案内は、ログイン前でも見られるのが一般的）。
  - 載せる内容（運営者の名前、事業内容、所在地、問い合わせ先、サービスの紹介など）と、文章を誰が用意するか。
  - リンクを置く場所（ヘッダーかフッター）。
- 作る時期の目安：トップページを整えるときに、一緒に作る。公開前に必要な「利用規約」「プライバシーポリシー」「特定商取引法に基づく表記」のページも、同じ仕組みで作れるので、まとめて作るのが効率的。

### ログイン前に、サービスの一覧を見られるようにする
- ログインしていなくても、サービスの名前・説明・料金・注意書きの一覧を見られるようにする。手間は小さく、ほかの機能に影響しない。サービスの内容は、すでにコード内の1か所（`app/services_catalog.py`）にまとまっているので、ログイン前の画面から、同じ内容を読み出すだけで済む。金額や文面は、1か所を直せば、ログイン前後の両方に反映される。
- 作るもの：誰でも見られる、読み取り専用のページ（または、トップページへの組み込み）。ログイン済みの画面にある「申し込む」ボタンは、ログイン前は「会員登録して申し込む」「ログインして申し込む」に置き換える。
- 決めること：
  - 置く場所：トップページ（`/`）に直接載せるか、専用のページ（`/services`）をログインなしでも見られるようにして、トップページからリンクするか。後者がおすすめ（「ログイン前は閲覧だけ、ログイン後は申込みもできる」1つのページにまとめられる）。
  - 見せる範囲：返金の規定や問い合わせ先も、ログイン前から見せるか。見せる場合は、公開前に作る規約や特定商取引法の表記と、内容をそろえる。
  - 「2件目以降のリリース作成」（枠の購入）：ログイン前は「無料で1件作成できます」と案内し、購入の案内は、ログイン後だけにするのが自然。
- 前提：サービスの金額と、税込・税別の表記を、公開前に確定してから公開する（仮の金額が、ログイン前から見えるようになるため）。
- 作る時期の目安：トップページと About Us を整えるときに、一緒に作る。

### そのほか、すでに決めてある保留事項
| 項目 | 内容 | 作る時期 |
| --- | --- | --- |
| トップページ | いまは「準備中です」という仮の画面。サービスの紹介や About Us へのリンクを置く | 公開前 |
| 画面の見た目 | いまは最小限の HTML。デザインをまとめて整える（CSP の追加も、このとき） | 公開前 |
| ログインなどの回数制限 | ログイン失敗、パスワード再設定の依頼、会員登録の回数を制限する | 公開前 |
| 返金・異議申し立ての通知の受け取り | Stripe の `charge.refunded` などを受け取り、購入した書類の枠と連動させる | **完了**（段階4） |
| Nginx の設定 | `client_max_body_size` を5〜6MB程度にする（写真のアップロードのため） | 本番の VM の設定のとき |
| ユーザー削除時のファイル削除 | 退会処理で、写真・Word・納品ファイルも削除する | **完了**（段階4） |
